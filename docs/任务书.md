## 1 文档目的与结论

在现有 MVP 上逐步完成正式交付改造，保留已经建立的收购、检测、整备、入库、销售、财务和审批页面。当前系统适合演示业务路径，但尚不适合直接承载客户正式业务数据。主要缺口是启动清库、业务事务、对象权限、真实审批约束、销售及收付款闭环、财务口径和文件存储。

本次已读取该提交下全部源码、模板、部署配置和说明文件，并核对原始《二手车业务管理系统软件开发需求说明书》及本次聊天约束。文档中的“已确认”指源码证据；风险判断不是对线上系统已发生事故的断言。

验证范围：完成 Python 源码语法解析和演示数据的独立数值复算。当前审查环境没有安装 Flask，未运行 Web 集成测试、并发测试、真实 OSS 上传或云端部署。下文验收用例是开发完成后必须执行的要求，不代表本次已通过。本次没有修改 GitHub 仓库或线上系统。

**实施原则：先保证数据和账目可信，再补齐正式交付能力，最后扩展外围功能。**

## 2 已确定的项目约束

1. 实施人员为项目负责人一人，配合开发工具。按顺序交付可验收的小批次，不采用三人团队配置。
2. 当前交付目标是一家二手车公司的内部管理系统。保留部门和员工的数据边界；本轮不建设多租户计费、租户开通、订阅套餐等商业 SaaS 平台。
3. Render 仅用于客户演示。正式运行部署在中国大陆；开发、演示、测试、生产的数据和凭据必须隔离。
4. PC 管理端优先；手机端先满足查车、拍照、视频上传和必要业务操作。后续微信小程序复用后端业务服务和 API。
5. 沿用 Flask 和 Jinja，先进行模块拆分和数据层改造。不因本次改进默认重写为其他语言、微服务或复杂前后端分离架构。
6. 图片、视频、合同扫描件等二进制文件进入对象存储；业务数据库保存元数据和关联关系。
7. 核心业务不依赖 AI 模型 API。车型识别、OCR、知识库或客户智能聊天单独立项，不作为登录、开单、审批和核算的前提。
8. 本文提出实施顺序，不自动缩减原需求范围。未实现的原需求要在交付清单中明确列为本期、后续或不含，不能直接宣称“全部完成”。

## 5 开发任务

### T01 分离生产启动与演示初始化

对应：F01、F09。修改 `Procfile`、`render.yaml`、`seed.py`、应用初始化和 README。

- 从所有生产启动命令中移除 seed。启动只加载应用，不删库、不导入演示账号、不自动生成演示交易。
- 将演示初始化改为显式命令，仅允许开发/演示环境执行；破坏性重置必须带明确参数，并校验目标数据库。生产环境即使传重置参数也拒绝。
- 初始管理员使用独立一次性命令建立，已有管理员时不覆盖密码。生产不得保留公开演示账号。
- 应用导入时不执行建表/迁移。数据库升级通过单独发布步骤执行，避免多个 Gunicorn worker 同时改结构。
- 生产缺少 SECRET_KEY、数据库连接等必要配置时拒绝启动，错误信息不得输出密码和完整连接串。
- 分离 `development`、`demo`、`testing`、`production` 配置，提供无真实密钥的 `.env.example`。

验收：创建车辆和订单后连续重启两次，数据、ID 和账号不变；生产执行 seed 重置被拒绝；缺少生产密钥启动失败且日志不泄密。

### T02 数据库与事务改造

对应：F02、F10、F19。修改 `db.py`，新增模型、数据库迁移和业务服务层。

建议采用 SQLAlchemy 管理数据模型与事务、Alembic 管理迁移，生产使用阿里云 RDS MySQL。具体小版本按正式环境可用且受支持的版本锁定。SQLite 仅保留本地快速演示用途；事务和并发验收必须在与生产同类的 MySQL 上完成。

- 金额用 `DECIMAL(14,2)`，Python 使用 `Decimal`；比例采用足够精度的 DECIMAL，金额按明确规则四舍五入到分。
- 一个业务动作使用一个事务。订单、车辆状态、成本/资金记录、审批执行和业务审计必须一致提交或回滚。
- 对收购、销售、整备登记、付款核销、审批操作设计幂等键；同一键同一内容返回原结果，同一键不同内容返回冲突。
- 增加外键、非空、金额范围及业务唯一约束。删除策略不得级联抹掉财务、合同及历史审计。
- 增加常用查询索引：状态及日期、收购员/销售员/部门、工单负责人、业务对象关联、审批待办、附件对象、资金单据。
- 状态迁移使用行锁或带旧状态/版本的条件更新。不能采用“先查一下、再无条件更新”的并发保护方式。
- 整备项目生成成本记录时保存来源类型、来源 ID 和唯一约束，避免重复计费。
- 将已存在的 SQLite 方言改为跨数据库模型查询或明确 MySQL 实现，特别检查 `date('now','localtime')`、`INSERT OR IGNORE`、`ON CONFLICT` 等。

验收：模拟业务写入中途失败，相关表均无半成品；重复请求不产生第二笔费用；并发建单只有一个有效占用；迁移前后金额合计与记录数可对账。

### T03 统一身份、对象和字段权限

对应：F04、F05、F09、F15、F18。修改所有路由、查询和模板。

建立“角色 + 操作权限 + 数据范围”的集中授权机制。页面按钮和后端规则使用同一权限定义，不能仅依赖隐藏菜单。以下为建议初始矩阵，客户确认后配置；不存在权限默认拒绝。

| 身份 | 建议数据范围 | 可执行操作 | 默认限制 |
|---|---|---|---|
| 系统管理员 | 账号及配置范围；业务查看单独授权 | 用户、权限、系统配置 | 不因管理员身份自动具备所有财务审批权 |
| 老板/授权管理层 | 公司业务汇总和明细 | 授权审批、经营查询 | 仍受审批自审限制和审计约束 |
| 财务 | 授权公司/部门财务、资料 | 核销收付款、资料核验、财务报表 | 不任意修改已核销金额 |
| 部门管理员 | 本部门 | 分派、查看本部门业绩、授权审批 | 不默认跨部门查客户和利润 |
| 收购员 | 本人负责的收购业务 | 建档、提交收购与检测资料 | 不读取不相关销售客户资料 |
| 销售员 | 可销售车辆的公开业务字段、本人订单 | 开单及本人订单办理 | 无权操作他人订单、查看未授权收购底价/部门利润 |
| 整备人员 | 分配给本人或授权范围的工单 | 整备登记、提交完成、查看必要车况 | 无权读取客户隐私和销售利润 |

- 统一 `require_current_user`，每次请求验证账号 active、会话版本/有效期；禁用后下一次请求失效，返回登录或 401，不能 500。
- 订单转移、交付、工单开始/加项/完成、车辆详情、审批列表和附件均校验对象权限。
- 整备详情提供可访问的受限视图，并修正工单 ID 与车辆 ID 混用。
- Dashboard 也按范围聚合；不能通过首页绕过财务权限。金额敏感字段在服务层裁剪，不发送到无权客户端。
- 新用户必须明确选择岗位，不默认管理员；增加修改密码/受控重置、账号禁用和会话吊销。
- 所有 CSV/附件下载执行与页面一致的权限检查，并记录导出事件。

验收：销售 A 对销售 B 的订单执行 GET/POST 均不可越权；修改 URL 中 ID 无法扩大范围；整备只见必要信息；禁用已登录账号后旧会话立即在下一请求失效。

### T04 基础 Web 安全与输入校验

对应：F09、F10、F17、F18。

- 所有基于 cookie 会话的写操作启用 CSRF，退出登录改为 POST。登录成功先清理旧会话，再设置新身份。
- HTTPS 生产配置启用 Secure、HttpOnly 和合适的 SameSite cookie；设置会话期限。代理信任只覆盖实际受控代理，不盲信请求头。
- 登录按账号与来源限流，错误信息不泄露账号是否存在；记录成功/失败和限流事件，记录中不含密码。
- 对金额、比例、里程、年份、评分、手机号长度、文本长度和状态枚举做服务器端校验。拒绝 NaN、Infinity、异常科学计数值和业务范围外数据。
- 评分统一为 0–100、最多一位小数；检测人从登录身份关联，展示姓名可保留快照。
- settings 更新集中校验、事务提交并保存旧值/新值；失败不写入半套设置。
- 保留模板自动转义，文件名/备注不直接作为 HTML。添加与页面兼容的安全响应头。
- CSV 对用户可控文本中的危险公式前缀进行安全处理；合法金额列保持数字，不把所有负数强行变文本。
- 锁定依赖版本并生成可复现安装清单，更新依赖后执行核心回归。

验收：无 CSRF 的 cookie 写请求被拒绝；非法金额得到字段错误且没有写库；脚本内容按文本展示；恶意 CSV 文本不会作为公式执行；普通金额的小数正确保留。

### T05 明确车辆生命周期与入库审核

对应：F06、F12、F14、F17；原需求 4.1、4.2。

区分“收购阶段”“车辆处理状态”“销售订单状态”，不要把所有流程塞进一个状态字段。允许提前录入验车资料，但只有业务条件满足才进入正式库存。

建议车辆主流程如下，具体名称可与现有中文页面兼容：

| 当前状态 | 操作 | 关键前置条件 | 结果 |
|---|---|---|---|
| 收购草稿/验车中 | 确认收购签约 | 必填资料、收购合同、所需审批通过 | 已签约待检测 |
| 已签约待检测 | 检测通过 | 合法结论、检测报告、必要附件 | 待整备，生成唯一有效工单 |
| 已签约待检测 | 检测退回 | 原因、经办人、后续退款/终止待办 | 已退回，不再计入经营库存 |
| 待整备 | 领取/分配工单 | 工单授权、无业务冻结 | 整备中 |
| 整备中 | 提交完成 | 必填项目、费用、必要资料完成 | 待入库审核 |
| 待入库审核 | 质检通过 | 当前版本标准全部通过、手续符合要求 | 在售，写入 stocked_at |
| 待入库审核 | 驳回 | 具体整改要求 | 整备中，保留本次质检记录 |
| 在售 | 销售订单生效并占用 | 无其他有效占用、销售条件满足 | 已预订/待交付 |
| 已预订/待交付 | 取消订单 | 授权、退款/解约处理要求 | 按规则释放为在售 |
| 已预订/待交付 | 交付 | T07 所有条件通过 | 已售出，写入 delivered_at |

- 上门验车可以是尚未收购的线索，不计库存，不计资产成本。
- “入库标准”从设置文本升级为有版本的检查项。每次审核保存该版本和逐项结果，不因修改设置重写历史结论。
- 库存至少区分：处理中车辆、正式在库车辆、可售车辆、已预订车辆、已售历史；避免一个数字同时表达不同口径。
- 单独记录收购确认、到店、检测、入库、交付、退回时间和操作者；不以 created_at 代替全部时间。
- 退回不是财务退款；退款尚未完成时保留应收/应退和待办，不直接删除记录。
- VIN 规范化并检查当前有效收购批次的重复。历史车辆再次收购是新经营批次，不应被永久 VIN 唯一限制阻断。历史演示 VIN 不符合新规则时进入迁移异常清单。

验收：不能跳过检测和质检直接在售；驳回后可查看整改要求和复检链；同一通过请求重试不生成第二张工单；建档时间与实际入库时间独立显示。

### T06 让审批真正控制业务

对应：F06；原需求 4.6。

新增业务关联字段：`business_type`、`business_id`、`business_version`、`submitted_snapshot`、`policy_version`、`decided_at`；多级审批记录独立步骤和操作者。

- 高价收购、特殊车况、收购价调整、销售优惠、特殊成交、报销分别定义触发条件和受控动作。
- 高价收购在确认签约/付款前校验审批；是否允许审批前开展上门检测由规则单独控制。审批不是“创建一条待办就算通过”。
- 销售优惠绑定订单价格快照；审批后改动价格、优惠或关键条款使旧审批失效，重新提交。
- 通过审批只允许执行该授权动作。报销通过产生待付款事项，不等于已经付款；付款仍需财务核销。
- 审批人必须属于该类型当前步骤授权范围；不能因为角色是 finance 就批准所有类型。
- 保留禁止自审；同一审批并发同意/驳回只有一次有效决策。幂等重试不得重复生成付款或成本。
- 首期采用有限的顺序审批节点配置，支持驳回、修改再提交；不引入通用 BPMN 引擎。
- OR 的业务含义、字段、流程和权限尚不明确。未确认前禁止猜测实现或显示为“已支持 OR”。

验收：高价审批待审/驳回时无法完成受控动作；已审批后修改价格必须重新审批；无权审批人即使构造请求也被拒绝；报销通过不会自动增加已付款金额。

### T07 销售占用与收付款交付闭环

对应：F03、F07、F08；原需求 4.3、4.5.6。

- 销售订单明确草稿、待审批、已确认、已取消、已交付等状态，并指定何时占用车辆。建议提交有效订单时原子占用，避免多个销售同时承诺同一辆车。
- 可新增 `vehicle_reservations`，以当前经营批次 ID 为主键/唯一键维护唯一有效占用，历史订单另行保留。MySQL 实现不要照搬只在其他数据库可用的部分唯一索引。
- 建单、占用车辆、绑定销售归属和日志放在一个事务；取消后在条件满足时释放占用。
- 定义报价、优惠、最终合同价：建议新单 `contract_amount = quoted_amount - discount_amount`。若界面录入的是优惠后成交价，字段和提示必须说明，不能再次减优惠。
- 旧 `price` 与 `discount` 的含义不能凭猜测迁移。每条异常单保留原值并交客户确认；示例奥迪单的 188000 与优惠 2000 不能直接推断为应收 186000。
- 增加收付款台账：订单/车辆、方向、类型（订金、尾款、贷款到账、收购付款、费用付款、退款）、金额、时间、方式、流水号、凭证、经办人、核销人、核销状态。
- 首期采用人工登记凭证和财务核销，不默认接银行支付或微信支付。销售只能提交收款记录，是否拥有核销权限单独授权。
- 金融流程区分申请、审批、放款、实际到账；“放款已批准”不等于公司已收款。
- 交付前在服务端重新验证：有效订单及占用、价格审批、收款满足应收要求、贷款到账、过户要求、财务资料核验、交付清单和交付单。
- 特殊允许先交车后收款或过户的情况必须独立授权审批，有原因、责任人、期限和未完成待办；默认不允许跳过。
- 交付与已售状态原子更新，交付时间只写一次。退订、退款、售后退车有独立流程，不通过编辑历史金额解决。

验收：两名销售同时提交只有一张有效订单；重复点击仅返回同一结果；未收足款/未放款到账/缺件/过户不满足时禁止普通交付；旧订单不能交付另一个有效订单占用的车辆。

### T08 修正财务与报表口径

对应：F08、F10、F12、F13、F14。

本模块先提供可信的经营台账；不能把简单经营利润表标为已经完成专业总账、资产负债表或法定财务报表。

| 指标 | 建议口径 |
|---|---|
| 在处理车辆数 | 已确认收购但未正式入库且未退回的经营批次 |
| 在库车辆数 | 已正式入库且尚未交付/退回的经营批次，含已预订 |
| 可售数量 | 在库且没有有效销售占用、冻结的车辆 |
| 单车归集成本 | 收购确认成本 + 已确认整备成本 + 其他归集费用 + 经确认分摊费用 |
| 在库车辆成本 | 在库车辆归集成本之和；待入库成本另列 |
| 实收/实付 | 已核销资金流水净额，包含有凭据的退款/冲销 |
| 已交付销售额 | 有效已交付订单的最终合同价，退车调整单独处理 |
| 已实现经营毛利 | 已交付销售额减对应已确认车辆成本，按统一截止口径 |
| 部门利润 | 依 T11 的内部结算及费用规则核算，未确认前不自动生成 |
| 提成应计/结算 | 依 T11 的车位规则和结算版本，不能使用所有最新订单简单相乘 |

- 数据库存在“其他”费用分类，但缺少完整录入、审核和纠错流程；补其他费用、部门费用、分摊批次及附件。
- 费用产生、费用审批、费用付款是不同事件。同一费用被核销付款不能再次计入成本。
- 更正采用冲销与重记并引用原记录；已确认的成本和资金不允许无痕覆盖。
- 已结算历史成本、提成保留快照；后续补计费用产生可追溯调整，不悄悄修改已发放提成。
- Dashboard、财务页和 CSV 调用同一个报表服务，使用一致的状态筛选、日期口径及金额精度。
- 收购、入库、交付、付款分别使用对应业务时间；明确业务时区为 Asia/Shanghai，存储时间策略保持一致。
- 删除当前“收购部利润 = -全部收购价”的展示，改为收购数量、收购确认金额等真实指标，直至部门核算上线。

回归基准：当前 seed 数据共有 12 辆，其中未售出且未退回 9 辆；这 9 辆的收购价合计 803000 元，整备成本 5700 元，总成本 808700 元。这个“9 辆”是旧状态下的广义未退出车辆数，不等于新口径的正式在库数量。页面若展示该合计必须标明覆盖哪些状态。正式入库口径应独立计算，不能机械将所有库存数字改成 9。

验收：新增待交付订单不增加已实现销售额/毛利；成本登记与付款核销不双计成本；页面和导出结果到分一致；交付跨月按交付日期归属；退款/冲销能追到原交易。

### T09 图片视频及合同附件存储

对应：F16；本轮生产交付必需。

**存储分工：RDS 保存业务和附件元数据；国内私有 OSS 保存原始文件和派生预览文件；ECS 运行应用。** 不将图片 Base64、视频二进制或永久公网 URL 塞进数据库，也不把应用服务器硬盘作为唯一文件存储。

上传流程：

1. 客户端申请上传任务，传业务类型、业务 ID、文件分类、声明类型及大小；后端验证业务权限、状态和额度。
2. 后端生成不可预测的对象 key 和上传任务，仅授权指定对象或最小前缀，使用短期凭证/签名。浏览器不得获得长期 AccessKey。
3. 图片可采用简单直传；大视频采用支持分片和断点续传的 OSS SDK/接口。不能假设单个 PUT 签名 URL 自动具备续传能力。
4. 客户端上传后提交完成；后端向 OSS 校验对象存在、大小、类型、校验信息和任务归属。不能只信客户端声称成功。
5. 使用幂等完成接口绑定附件；失败保留可恢复状态。超时任务和孤立文件进入延迟清理队列。
6. 展示或下载时再次检查对象权限，签发短期访问 URL。数据库保存 bucket/key，需要时临时生成 URL，不保存会过期的签名地址作为永久地址。

附件至少包含：ID、业务关联、所属车辆经营批次、分类、原文件名、bucket、object_key、对象版本（若启用）、MIME、字节数、校验和、上传人、上传时间、处理状态、预览关联、删除标记、删除原因和保留控制字段。

- 分类覆盖验车照片/视频、内外部检测报告、收购合同、销售合同、证件、付款凭证、整备前后记录和交付单。
- 原图/原视频作为证据保留；缩略图、压缩预览和封面独立对象，不能无提示覆盖原件。对外营销图片与内部证据分类。
- 手机上传提供进度、失败重试、断网恢复、选择文件和拍摄入口。兼容性不支持的格式给明确提示，不能显示成功后无法查看。
- 文件白名单、服务端类型检查、文件大小和数量限制、账户/业务容量额度必须生效；对 PDF 等附件采取安全下载与受控预览策略。
- 可配置初始产品限额，例如单图 20MB、单视频 500MB；这是建议业务限制，并非 OSS 产品上限，需用客户实际设备文件验证后调整。
- 缩略图/转码通过有持久任务记录的后台 worker 或云媒体服务执行；任务可重试。首期不要在 Web 请求中同步转码大视频，也不要只起易丢失的后台线程。
- 证据附件删除采用可审计流程；普通员工不能直接永久删除。原件保留期限、归档节点由客户确认，不擅自按 90/180 天自动删除。
- 已售车辆文件可按确认的访问频率转低频/归档存储；归档可能需要恢复等待和读取费用，页面必须能表达恢复中状态。
- 设置未完成分片清理、孤立对象核查、容量趋势和费用预警；对象版本控制不等于独立备份。

验收：跨员工猜附件 ID 不能下载；无授权不能获取上传凭证；超限文件被拒绝；视频中断可恢复；伪造完成请求不能生成可用附件；预览压缩后原文件仍可取回。

容量示例仅用于测算：每月 100 辆，每辆 40 张原图、平均 3MB，另有 3 段视频、每段 100MB，则新增原始文件约 42GB/月、504GB/年，约 51600 个文件/年。缩略图、转码、版本和备份另计。文件容量增长主要发生在 OSS，不应逼迫数据库同比扩容。

费用拆为存储、下载/观看流量、请求、图片处理/视频转码、归档恢复、版本与备份。向客户交付时列为持续云资源费用，不承诺一次开发费包含无限存储和无限流量。

### T10 资料核验和合同基础能力

对应原需求 4.1.2、4.3、4.4、4.5.6。

- 卖方/原车主、买方客户、联系人及供应商使用明确字段和对象，避免当前“客户姓名”混用。
- 按收购、入库、销售、交付定义必备材料清单，区分已上传、待核验、已核验、驳回、过期/被替换；关联实际附件，不能只放一个“资料齐全”勾选框。
- 财务核验记录操作者、时间、结论、驳回原因和被核验文件版本；更换关键附件使相关核验失效。
- 合同支持编号、模板版本、录入字段、生成/上传、打印下载和原件归档。已签约版本不能被新模板覆盖。
- “生成合同 PDF/上传签字扫描件”与“有第三方电子签章服务的电子签约”分开标示；后者单独确认供应商和费用。
- 售后基础档案可在后续批次实现：关联已售订单、质保方案/期限、服务记录、维修附件和到期提醒。具体赔付规则不猜测。

验收：缺失必备交付资料时无法普通交付；替换关键合同后核验状态重置；下载合同遵循权限；历史签约合同内容保持不变。

### T11 车位提成和部门独立核算

对应：F13；原需求明确的核心业务，不能仅作为视觉优化延后。

先完成可支持规则的数据结构：车位档案、车位到位/离位记录、车辆与员工归属履历、部门归属快照、提成规则版本、应计明细、结算批次及调整记录。

下列问题在客户确认前属于阻断自动结算的事项：

| 需确认问题 | 未确认时的处理 |
|---|---|
| “车位”指物理位置、员工配额还是业务结算单位 | 建档字段可准备，但不启用自动计算 |
| “到位”认定时间、证明材料、谁确认 | 保留人工记录及审计，不自行推定 |
| 收购员与销售员如何分别计提，按成交额、毛利还是固定金额 | 只展示待确认测算，不生成可发放工资 |
| 换车位、换员工、跨月成交的归属 | 保存完整履历，不用当前责任人覆盖历史 |
| 亏损、退订、退车、迟到成本、分期回款如何处理 | 不采用默认负提成或自动扣款 |
| 收购部与销售部内部结算价、部门费用和利润分配 | 暂停自动部门净利润和分红计算 |
| 管理人员月/年利润对应薪酬与分红的具体公式 | 与财务规则确认后再上线工资结算 |

- 规则确认后建立至少一组客户认可的算例：正常成交、换车位、换员工、跨月、亏损、退车和补计费用。
- 结算明细关联车辆经营批次、订单、车位履历、员工、部门、金额基数、规则版本和计算过程。
- 结算后调整以新调整单体现，修改全局比例不追改历史已结算金额。
- 部门利润必须防止将公司对外成本与部门内部结算重复计入公司总利润。
- 工资与分红是独立结算模块，不能把“提成汇总”页面改名后宣称支持完整薪酬。

验收：客户确认算例逐项算对；历史换人换车位可追溯；修改比例不改变已结算批次；退款可追到原提成并生成调整。

验收：状态表不出现 Python 方法字符串；分页前后无重复/漏项；详情跳转正确；手机可完成拍摄上传、失败重试和必要提交。

### T13 审计和关键数据保护

- 保留现有操作日志并升级结构：操作者、角色/部门快照、动作、业务类型和 ID、前后差异、原因、时间、请求 ID、结果。
- 成功的核心业务日志与业务事务一致提交；登录失败、越权和安全事件单独记录。
- 不记录密码、密钥、完整令牌或长期签名链接；客户隐私字段按需求脱敏。
- 已核销资金、已签合同、审批决策和已结算提成禁止普通后台直接删除。修正必须有引用关系和原因。
- 原需求提出日志永久留存，架构上需支持归档和查询；与客户确认最终留存制度、访问权限和成本后实施。归档不能使业务关联丢失。
- 补操作日志查询与授权导出，关键配置修改能看到旧值和新值。

验收：同一车辆能追溯审批、费用、收付款、资料和交付全过程；更正能定位原记录；业务人员不能通过接口删掉已核销资金或已签合同。

### T14 国内生产部署与运维

正式方案采用“国内 ECS + RDS MySQL + 私有 OSS”，同一国内地域部署，ECS 与 RDS 使用 VPC 内网。客户持有云账号和资源，开发维护使用最小权限子账号。

| 组件 | 用途 | 配置要求 |
|---|---|---|
| ECS | Flask/Gunicorn、反向代理及轻量后台任务 | 4 核 8GB 可作为小规模试运行的评估起点，最终按实际并发和任务压测选择，不是容量保证 |
| RDS MySQL | 业务、权限、财务及附件元数据 | 独立托管实例；50–100GB 可作为起步测算，按增长监控扩容；不公开数据库端口 |
| OSS 私有桶 | 原件、预览、视频、合同 | 以实际增长计量；最小权限访问、分片上传、生命周期和恢复策略 |
| HTTPS 入口 | PC/H5/API 访问 | 域名、证书、反向代理超时及上传相关配置 |
| 备份与监控 | 故障发现与恢复 | 数据库备份、日志、资源/错误/费用告警和恢复演练 |

- 具体数据库规格、可用区、备份保留和云资源报价在采购时确认；不能把演示环境参数直接当生产容量方案。
- 提供 Dockerfile 或可复现部署脚本，选择一种主要部署方式；单机阶段不需要 Kubernetes。
- 凭据放环境配置/受控密钥服务，不进入仓库、镜像或前端。对客户敏感字段明确传输加密、云盘/数据库/对象存储加密策略；需应用层加密的字段单独设计密钥和查询方式。
- 生产健康检查区分进程存活和依赖可用，不返回内部连接信息；进程异常自动重启，监控错误率、延迟、数据库连接、磁盘、失败上传、任务积压和证书到期。
- 设置日志轮转，文件不无限写满系统盘。转码等资源密集任务设并发上限，必要时单独 worker。
- 数据库恢复目标建议先与客户确认，例如 RPO 不超过 24 小时、RTO 不超过 4 小时；实际能力以备份频率、日志恢复和演练结果为准，不能写了自动备份就算达标。
- 数据库备份不包含 OSS 文件。分别规划文件版本/备份、附件索引关联恢复和误删除恢复；至少完成一次数据库加文件的联合恢复演练。
- 域名和国内访问所需手续由客户与云服务商确认办理；未验证前不在项目中标记为已完成。
- 维护交接包含资源清单、发布/回滚/恢复步骤、故障联系人、账号权限、云资源续费责任；文档不明文记录真实密码。

验收：部署在国内目标环境后完成全链路测试；重启与重新发布不丢数据；数据库仅允许授权来源；备份可实际恢复；关键失败能产生告警。

### T15 为微信小程序预留接口

- 将业务逻辑从 Flask 路由提取到服务层，现有 Jinja 页面继续可用，后续 API 调用同一服务。
- 优先提供 `/api/v1` 下的身份、车辆查询、检测、工单、附件上传、订单和审批接口；本期只实现手机业务实际需要的部分，不必一次复制全站。
- 统一响应字段、分页、错误码、日期格式、金额字符串表示和幂等机制，提供 OpenAPI 或等价接口说明。
- 网页保留 cookie+CSRF；未来小程序采用适合其客户端的身份令牌方案，独立处理刷新、吊销和绑定企业员工账号。
- 微信身份不自动获得企业权限；仍执行员工 active、角色和对象权限。手机定位/IP 可作为额外风控条件，不能取代身份授权。
- 小程序不是将网页代码直接转换；未来另建小程序页面和登录适配，复用的是业务服务、数据库和文件系统。

验收：同一权限和业务规则能通过网页与已实现 API 得到一致结果；API 文档能说明失败、越权、重复请求及分页行为。

迁移到包结构时修正原 `app.py` 与新 `app/` 的命名/导入关系，同步调整 Gunicorn 入口。不要只创建空目录并保留所有业务继续堆在原路由文件。

## 8 旧数据迁移与回滚

1. 先确认演示库是否仅有虚构数据。没有真实业务时可创建干净生产库，不必把演示交易带入生产；如有真实业务，必须迁移和逐项核验。
2. 迁移前只读备份 SQLite 和附件目录（如后续已存在），记录文件校验值、各表行数、状态数量和金额合计。
3. 生成异常清单：重复/无效 VIN、孤立关联、多个有效销售订单、价格与优惠歧义、缺失审批、日期缺失、金额精度异常。
4. 对金额按明确规则转 Decimal；报告任何舍入差异。不得静默合并重复订单、推断付款已经完成或补造审批通过记录。
5. 旧 created_at 保留为创建时间；无证据的 stocked_at/delivered_at 保留未知或标为待确认，不能使用迁移时刻伪装历史。
6. 数据迁移脚本支持 dry-run、幂等和校验报告；对行数、主外键、成本汇总、已交付销售额、员工归属逐项核对。
7. 正式切换安排短暂写入冻结，完成最终导出、迁移、校验、切换和冒烟测试；不要让两套数据库各自接收新业务。
8. 回滚必须区分应用版本与数据。若新系统已产生新交易，回滚前先保存/核对增量；不能直接恢复旧快照丢弃新交易。
9. 发布迁移采用兼容性步骤，必要时先加字段、回填再切换代码，最后移除旧字段。禁止依靠启动时自动 drop/create。

## 9 分批实施顺序

| 批次 | 任务 | 依赖与完成门槛 |
|---|---|---|
| A 保护现有数据 | T01、T04 的密钥/CSRF基础；修复 F11/F15 显示和链接 | 可安全重启；演示与生产隔离；不改变财务公式来掩盖缺口 |
| B 数据及权限基础 | T02、T03、T13 基础 | 迁移可核验；事务和对象权限测试通过 |
| C 收购整备及文件 | T05、T06 收购审批、T09、T10 收购/入库资料 | 手机上传到私有 OSS；高价审批和入库门禁生效 |
| D 销售及财务闭环 | T06 销售/报销、T07、T08、T10 交付资料 | 防重复销售；付款、资料、交付和报表对账通过 |
| E 核心特色规则 | T11、T12，补充客户已确认的售后/岗位范围 | 车位和部门算例已确认；结算快照通过；不能把未确认规则算作交付完成 |
| F 正式交付 | T14、必要的 T15、迁移演练和全量核心验收 | 国内测试环境验收、恢复演练、文档交接、客户确认后上线 |

客户对 T11 的规则确认应在批次 A/B 期间推进，以免后期推翻财务模型。规则不清只阻断相应自动结算，不阻断其他已明确模块开发。

每批次提交一组可审查变更，说明任务 ID、改动文件、数据库变更、测试结果和待确认事项。不要一次性将全部任务交给工具进行不可审查的大改，也不要只改样式后宣称完成生产化。

## 10 必须执行的验收清单

以下用例既包含自动化测试，也包含人工/云环境验收。不要用大量“函数返回某字段”的测试替代业务测试。

| 用例 | 场景 | 通过标准 |
|---|---|---|
| A01 | 保存业务后连续重启/发布 | 数据和账号不丢失，seed 不执行 |
| A02 | 生产重置命令及缺少密钥 | 拒绝重置；缺密钥启动失败；无敏感日志 |
| A03 | 中途写库失败 | 单据、状态、成本、审计完整回滚 |
| A04 | 两人并发销售同一辆车 | 只有一个有效订单占用，另一个返回可理解的冲突 |
| A05 | 重复整备加项/付款核销/交付 | 一次业务效果，重试返回同一结果 |
| A06 | 相同幂等键但不同金额 | 返回冲突，不复用错误结果 |
| A07 | 销售访问及操作他人订单 | 后端拒绝，无金额/客户信息泄露 |
| A08 | 普通员工查看全部审批/跨部门数据 | 返回范围内数据，不能靠 URL 或筛选越权 |
| A09 | 整备人员访问车辆 | 可见必要技术资料，不见未授权财务和客户资料 |
| A10 | 已登录用户被禁用 | 下一请求会话失效，无 500 |
| A11 | 无 CSRF、非法金额、非法状态 | 返回明确错误且无业务写入 |
| A12 | 高价收购审批未通过 | 不能完成被控制的签约/付款动作 |
| A13 | 优惠审批后修改价格 | 原审批失效，重新提交 |
| A14 | 并发审批同意/驳回 | 一次有效决策，下游不重复执行 |
| A15 | 入库缺项/质检不通过 | 无法在售，退回带原因且可复检 |
| A16 | 重复检测通过 | 不生成重复有效整备工单 |
| A17 | 未收足款、贷款未到账或资料缺失 | 普通交付被拒绝 |
| A18 | 交付旧/取消订单或他人占用车辆 | 被拒绝，车辆和新订单状态不受影响 |
| A19 | 新建未交付销售订单 | 已实现销售额、毛利和已结算提成不增加 |
| A20 | 成本登记后付款核销 | 成本不重复增加，实付按核销增加 |
| A21 | 退款、成本冲销及补记 | 可追溯原记录，报表按规则调整 |
| A22 | 跨月创建、交付、付款 | 各报表按对应业务事件归属月份 |
| A23 | 页面与 CSV、金额带小数 | 同筛选结果一致，金额到分，危险文本不执行公式 |
| A24 | 原始演示数据复算 | 12 条历史记录；旧口径 9 条未退出记录的成本合计 808700，页面标签解释口径 |
| A25 | 私有文件跨用户访问、签名过期 | 未授权不可访问；过期需重新授权 |
| A26 | 视频断网续传和伪造上传完成 | 续传可完成；不存在/不匹配对象无法绑定成功 |
| A27 | 图片预览、合同替换及删除 | 原件不被覆盖；关键核验失效；删除有授权及审计 |
| A28 | 换车位/换员工/改比例/退车 | 客户算例正确，历史结算不被覆盖 |
| A29 | 部门内结算和公司汇总 | 公司层面不重复计算内部收入或成本 |
| A30 | 首页状态表、工单链接及分页 | 无方法对象文本，跳转正确，分页稳定 |
| A31 | MySQL 迁移与并发测试 | 无 SQLite 方言错误，约束与事务符合预期 |
| A32 | 数据库与 OSS 联合恢复 | 单据、附件关联和可读文件恢复到已验证时间点 |
| A33 | 国内部署与权限配置 | HTTPS 正常、数据库非公网开放、凭据不入库、不入仓库 |
| A34 | 手机端实际设备试用 | 能查车、拍摄上传、看到进度并从失败中恢复 |

性能验收在客户给出人数、日操作量和文件规模后锁定。可先用一万条车辆历史记录和二十个并发业务用户做试验性基准，记录列表/详情/审批接口的 P95、查询数与错误率；这是假设测试规模，不是已验证承载能力。大文件速度单独测量，不与普通 API 响应时间混算。

## 11 待客户确认的业务决策

这些问题需要最终明确，但开发工具可以先完成不依赖它们的安全、事务和基础功能。

1. 车位定义、到位标准、收购和销售的提成公式及归属规则。
2. 部门独立核算的内部结算价、费用分摊、亏损和分红规则。
3. 成交价与优惠字段含义；财务经营收入确认、关账和调整办法。
4. 哪些收购/付款/优惠必须审批；每级审批人和代理规则；OR 的实际业务含义。
5. 特殊先交车后付款/过户是否允许，谁审批，后续如何追踪。
6. 必备合同、证件、检测报告、交付单及核验人。
7. 图片视频每车平均量、单文件大小、日/月新增车辆、保留期限、归档读取要求。
8. 哪些角色可以看到底价、利润、客户电话、跨部门信息和导出。
9. 首期是否包含售后、薪酬、摄影/主播/后勤；补充商城、物流、资产和知识库是否单列。
10. 微信/手机登录、IP/定位限制的优先级及使用场景。
11. 正式账号数量、同时在线人数、备份恢复目标、维护窗口及售后维护范围。
12. 云资源、域名、短信、电子签章、存储流量及后续 AI 调用费用由谁支付。

未确认的业务规则在界面与验收记录中标为“待确认/未启用”。不得自行编公式、伪造业务规则确认记录或默认全部审批通过。
